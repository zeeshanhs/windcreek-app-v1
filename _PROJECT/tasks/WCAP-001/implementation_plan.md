## Architecture decisions

| Concern | Implementation decision |
| --- | --- |
| Routes | Use App Router pages for `/`, `/login`, `/orders`, `/orders/new`, `/orders/[orderId]`, `/chats`, `/chats/new`, and `/chats/[chatId]`. The client session gate routes `/` to the signed-in destination or login after reading tab session state. Overlay destinations use the parent URL with `panel=order`, `panel=close-order`, `panel=photo`, or `panel=source&sourceId=…`; validate panel/ID combinations before displaying protected content. |
| Rendering boundary | Keep route/layout and metadata modules as Server Components. Put browser storage, demo session, forms, selectors, chat interactions, and dialogs inside the smallest practical Client Component boundary. Protected routes initially render a neutral loading/auth gate, never fixture titles or chat text in server HTML. |
| Demo storage | Use a versioned browser-local IndexedDB store as the canonical record store for users, orders, remarks/events, chats/messages, sources, sent photo blobs, and operation receipts. Seed the exact §6 fixtures once, including Morgan's five chats and Sam's separate CH-S01. Use one transaction for each write, a separate relationship store keyed by `(ownerUserId, orderId)` only for linked chats, and stable operation IDs/receipts for create, close, remark, chat creation, and send. General chats have no relationship-store row, so multiple general chats per user remain possible. Publish committed changes through a small subscription layer and `BroadcastChannel` so open tabs refresh their views. Do not create server process globals or per-route fixture copies. |
| Storage limits | IndexedDB keeps demo records in this browser across reloads and account switches until **Reset demo** clears and reseeds them. Other browsers/devices have separate datasets; private mode, quota errors, or cleared site data can erase them. Broadcast updates are best effort, so reads and mutation transactions recheck canonical records. There is no backend, real shared property data, or production concurrency guarantee. State these limits in the README and handoff. |
| Session | Accept only the four published fictional `@example.com` accounts with password `demo`; store the active demo user ID in tab session storage, never the password. Sign out/expiry clears the user, protected rendered state, pending chat drafts and staged unsent photos while retaining committed demo records. Direct protected URLs restore only after successful sign-in. This is a UI demonstration, not a security boundary for browser data. |
| Clock | Store the fixed 24 Sep 2026 10:30 UTC scenario clock with the seeded records; use explicit deterministic increments for committed demo actions (the specified create at 10:31 and close at 10:35 in those scenarios). Derive Today/Yesterday from this clock, not the visitor's local clock. |
| Operations | Centralize typed selectors and mutations instead of editing order or chat objects in components. Acknowledged IndexedDB transaction completion is success. Failed writes leave canonical state unchanged; an injected test fault after commit exercises uncertain-result reconciliation by operation ID. On version conflict or already-closed order, reread the current record and preserve the user's note without a second mutation. |
| Simulated answers | Use a deterministic response adapter keyed to the supported demo prompts/context, with source IDs and locators carried on each answer. It must handle unknown TEST-X9, bounded photo/visual categories, DF-S03 progressive identification, source gaps, safety handoff, and honest fallback. Do not suggest actual inference or retrieval. Inject delayed/failure results in focused tests; attach each result to its owning chat ID. |

Native IndexedDB avoids an added runtime dependency and gives the unique-key transaction needed for two-tab linked-chat races. If browser storage is unavailable, show the specified unavailable/retry state instead of silently switching to an inconsistent route-local store. A small adapter interface should keep persistence and fault injection testable. The app must clearly show **Prototype · Fictional data**, **Use demonstration credentials only**, and **Demo source** where relevant.

## Data and invariant work

1. Define strict types for `User`, `Order` (`open | closed` only), `Remark`, `OrderEvent`, `Chat` (nullable `orderId`), `Message` and delivery state, `Photo`, `Source`, unknown-fault record, and operation receipt. Use stable IDs and explicit owner/requester/actor IDs. Preserve the exact six initial orders, issue/location catalogs, four CH-D01 messages, other chat specimens, DF-S01/02/03 text, and specified dates. Do not infer equipment from an issue label when the fixture says **Not identified**.
2. Make order count, detail, linked-chat context, and order-information dialog selectors read one canonical order record. `createOrder` validates IDs/remark/requester and returns SO #1043 once for the specified first create fixture; `closeOrder` requires a fresh open version and nonblank note, records actor/time/note once, and leaves chats intact. `addRemark` is its own acknowledged write and rejects closed orders.
3. Make `getOrCreateLinkedChat(userId, orderId, operationId)` atomic with the unique relationship index. Existing Morgan/Sam records resolve to CH-D01/CH-S01 respectively. Avery gets one new linked entry immediately, even without a message. General chats start with `orderId = null`, are saved only on first successful send, and are never merged by equipment mention.
4. Preserve message IDs through sending, failed send, retry, answer delay/failure, and navigation. Keep the unsent composer draft and scroll position per chat in session memory. Stage one actual PNG/JPEG at most 10 MB before Send; preview the selected bytes and revoke temporary object URLs. Store sent bytes only as local chat attachments. Unknown-code logging has its own acknowledged receipt and failure state.
5. Keep source references structured (`sourceId`, type, version, locator, availability, supporting passage). Source links must point to DF-S01/02/03 or a real order remark/status when those support the statement. Represent the missing `assets/ahu1-points.pdf` as unavailable with no invented page, preview, or download.
