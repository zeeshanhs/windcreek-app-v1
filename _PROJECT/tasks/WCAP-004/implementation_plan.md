# WCAP-004 implementation plan — authenticated AskPat operations

## Goal and starting point

Add a demo-only server session and a validated, owner-aware HTTP API over the WCAP-003 SQLite/Drizzle repository. Keep the current IndexedDB screens and their browser records working until WCAP-005. The API must support the current order and chat workflows, including AHU-15 follow-ups, without treating the scripted ticket summary as an order or claiming a live integration.

WCAP-003 is implemented and its handoff reports passing migration, seed, and transaction tests. The current repository already has actor-scoped chat/photo reads, shared demo orders, immediate write transactions, a unique owner/order linked-chat constraint, and operation receipts. It does **not** have server sessions or routes; `appendMessage`, `putPhoto`, and answer generation are separate calls; `listOrders`/`listChats` are unbounded; and `seedBaseline` checks required seed IDs but does not prove that no later SQL records or modifications exist. These are implementation work, not assumptions that WCAP-003 already solved them.

Follow `AGENTS.md` and `docs/CONTRIBUTING.md`; preserve the clean starting tree and any later unrelated changes. The installed Next 16 guides confirm `app/**/route.ts` handlers, asynchronous `cookies()`, `runtime = 'nodejs'`, request-time route reads, and that `middleware.ts` is deprecated in favor of `proxy.ts`. Put authorization in each handler/shared server helper, including binary reads, rather than relying on a UI gate or proxy. Recheck the relevant installed guides during implementation.

## Contract and security decisions

1. **Session.** Authenticate only the four seeded fictional accounts by normalized email and the existing `demo` password convention. Label the endpoint and docs as prototype authentication. Add a versioned migration for server sessions with an opaque random token hash, user ID, expiry, and revocation state. Sign the cookie value with a server-only HMAC key from an ignored `.env.local` setting; reject absent, malformed, expired, revoked, or invalidly signed cookies. Store no clear token or password in SQL, and return only the public user DTO. Set `HttpOnly`, `SameSite=Lax` or stricter, `Path=/`, a finite `Max-Age`, and `Secure` on HTTPS; allow non-secure cookies only for local HTTP development. Logout revokes the current session server-side and expires the cookie. Never accept `ownerId`, `actorId`, or `requesterId` from an HTTP body as authority.
2. **Mutation defense.** Centralize authentication, exact same-origin `Origin` checking against a configured server origin, and appropriate Fetch Metadata checking for every cookie-authenticated POST/PATCH/DELETE, including login, logout, photo upload, and reset. Reject a missing or foreign origin with a stable 403 error; do not enable credentialed cross-origin access. Derive the expected origin from trusted server configuration, not an untrusted forwarded host header. Document local origin configuration and the cookie policy. Read routes must not mutate or seed data.
3. **Route/runtime boundary.** Keep `better-sqlite3`, secrets, and command code in `server-only` Node modules under `lib/askpat/`; make every API route explicitly Node runtime. Open only an explicitly migrated/seeded database; fail clearly when setup is missing. Avoid importing server code into current client components. Return `Cache-Control: no-store` for session and private data, including photos.
4. **Input and error shape.** Define narrow Zod request schemas at the HTTP boundary, with trims, field length limits, enum checks, operation ID format, and rejected unknown authority fields. Reuse/extend WCAP-003 domain DTOs for outputs. Use `{ data: ... }` on success and `{ error: { code, message, details? } }` on failure. Specify `401 UNAUTHENTICATED`, `403 FORBIDDEN_ORIGIN`, `404 NOT_FOUND` (also for another user's chat/photo), `409 VERSION_CONFLICT` or `OPERATION_CONFLICT`, `413 FILE_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`, `422 VALIDATION_ERROR`, and `500 INTERNAL_ERROR`; avoid leaking SQL internals. A stale close should include the current order/version in a typed 409 payload so WCAP-005 can refresh its dialog. Use appropriate 201/200 responses for new/replayed operations.
5. **Bounded reads.** Add SQL-level filtering and deterministic, cursor-based pages for orders and owner-scoped chats, with a documented maximum page size (for example 50) and stable sort keys. Page chat messages by ordinal so the twelve AHU-15 authored turns are followed by ordinary sends. Include `nextCursor`/`hasMore` consistently. Do not fetch entire tables and slice in handlers. Keep the existing order-detail history and citation placements intact.

## Proposed HTTP surface

Write a versioned API contract in `docs/ASKPAT_API.md` before or alongside handlers; the following names are the intended route map. Every route except login requires a valid server session. Mutation bodies carry a client-generated `operationId` where a retry could duplicate a record. The server supplies actor IDs from the session.

| Method and path | Request and result |
| --- | --- |
| `POST /api/askpat/session` | Demo email/password login; creates cookie; returns current user and session expiry. |
| `GET /api/askpat/session` | Session/bootstrap: user, expiry, issues, locations, fictional user display names, and reset generation. No password or secret. |
| `DELETE /api/askpat/session` | Revoke session, expire cookie, return 204. |
| `GET /api/askpat/orders` | Bounded search/status/sort page of shared demo orders. |
| `GET /api/askpat/orders/[orderId]` | Order detail with remarks, events, closure, and version. |
| `POST /api/askpat/orders` | `{ issueId, locationId, remark, operationId }`; create using session user as requester. |
| `POST /api/askpat/orders/[orderId]/remarks` | `{ text, operationId }`; return updated order. |
| `POST /api/askpat/orders/[orderId]/close` | `{ note, expectedVersion, operationId }`; return updated order or typed 409. |
| `GET /api/askpat/chats` | Bounded owner-scoped page, optionally filtered by general/linked and search. |
| `GET /api/askpat/chats/[chatId]` | Owner-scoped chat metadata and first message page, including scenario metadata. |
| `GET /api/askpat/chats/[chatId]/messages` | Owner-scoped next ordinal page; include references and photo metadata, never BLOB bytes. |
| `POST /api/askpat/chats/linked` | `{ orderId, operationId }`; return the one owner/order chat, existing or new. |
| `POST /api/askpat/chats` | `{ title, operationId }`; create an explicit general chat. |
| `POST /api/askpat/chats/[chatId]/messages` | Text plus optional one PNG/JPEG in bounded multipart form data, with `operationId`; atomically persist user message, deterministic answer, references, and receipt, or return a documented recoverable state. Return IDs and committed messages/chat state. |
| `POST /api/askpat/chats/new/messages` | Same send contract; create a general chat and send in one idempotent command so the existing New chat flow cannot strand an empty chat after a retry. |
| `POST /api/askpat/chats/[chatId]/equipment-choice` | `{ promptMessageId, useNewUnit, operationId }`; record the FCU-D02 choice and conversation-only equipment context once. |
| `POST /api/askpat/chats/[chatId]/faults/[messageId]/retry` | Idempotently retry a pending TEST-X9 log from stored message/context; never accept an arbitrary actor, target chat, or new diagnosis from the body. |
| `GET /api/askpat/photos/[photoId]` | Owner-scoped binary image response with verified MIME, safe content disposition, and `no-store`. |
| `GET /api/askpat/references/[referenceId]` | Resolve an accessible message's citation/source/order-reference metadata; order/source detail uses the existing fictional source records. |
| `POST /api/askpat/reset` | Explicit `{ confirmation: "RESET_DEMO" }`; atomically restore SQL seed, advance reset generation, revoke active sessions, and expire caller cookie. All clients re-bootstrap/sign in. |

The send multipart endpoint is the **photo upload** operation: bytes are attached to a new message in the same command, not uploaded as an orphan. Enforce one file, PNG/JPEG MIME plus file signature, a 10 MiB file maximum and a bounded total request size before parsing/allocating the full body; reject zero-byte/invalid payloads. Do not include binary or data URLs in JSON. Keep the six existing AHU-15 citation images and their metadata mapping as authored content; this task does not change the current browser UI or its static asset URLs. Document that those already-public static image URLs are outside the new private-photo endpoint.

## Server command work

1. **Adapt the repository port without weakening ownership.** Add actor-aware list/detail and command methods where required by the route map. Keep shared order visibility as the current demo rule, but scope chats, messages, photos, faults, and receipts in SQL predicates. Validate related message/photo/chat ownership in each write transaction. Keep the unique `(owner_id, order_id)` index and use immediate transactions/constraints for races. Add a new migration for sessions, reset generation, and any command state needed; never edit migration `0000`.
2. **Preserve order behavior.** Use the current create/remark/close repository semantics and deterministic runtime clock. Check a receipt before any state conflict check; the same actor/key/input returns the original result, while a key reused with different input returns `OPERATION_CONFLICT`. Keep remarks and events in order. A stale or already-closed request returns `VERSION_CONFLICT` and the current order without overwriting the first closure.
3. **Make send a single logical operation.** Refactor `demoAnswer` into a pure server-usable function over the WCAP-003 DTOs while preserving its bounded response text, reference IDs, equipment prompts, and AHU-15 rules. In an immediate transaction, verify owner, allocate IDs/ordinals, create the general chat if requested, insert the user message/photo, calculate and insert the answer/references, and write one receipt binding actor, kind, canonical input (including a photo digest), and result IDs. Replay returns those IDs without a second message or answer, including after response loss or server restart. Keep the scripted AHU-15 twelve messages and their reference rows untouched; append at ordinal 13 onward and never create an order from scenario metadata. A closed linked order still allows chat sends.
4. **Fault and equipment follow-up state.** For TEST-X9, keep the answer's uncertainty wording and store the unknown-fault record idempotently. If fault logging is deliberately separated from the message/answer commit, persist an explicit `pending` status with the committed answer and receipt, expose it in the response, and make the retry endpoint finish it once; a failed write must never silently leave a duplicate user message. The equipment-choice command must verify the referenced assistant prompt belongs to the actor's chat, append at most one choice result, update only chat equipment, and leave the linked order unchanged. Specify these states and recovery responses in the API contract.
5. **Reference resolution.** Chat DTOs already carry typed references and inline citation metadata. Resolve a reference by joining through its message and owner-scoped chat; return the existing synthetic source details, order target, or citation page metadata needed by the current panels. Validate target kind and existence. Keep photo authorization independent of any reference ID.
6. **Reset and pristine check.** Refactor WCAP-003 reset so the API uses the same transaction and baseline insertion as the CLI. Ensure session rows are revoked/deleted before seeded users are replaced, and a durable generation increments even when domain counters return to baseline. Implement a server-only `isPristineBaseline(connection)` for WCAP-005 that compares **all** domain tables and their meaningful values against the deterministic seed, including order versions/history, messages and rich JSON, references, photos/faults/receipts, and runtime counters. Ignore auth sessions/reset generation when assessing domain pristine state. Baseline counts or seed-marker presence alone are insufficient. It must return true after setup/reset and false after any domain mutation, without modifying the DB. Do not expose an import endpoint or this pristine check to ordinary chat sessions.
